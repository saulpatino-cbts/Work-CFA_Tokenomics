# NNNN. Decision title

- **Status:** Proposed | Accepted | Rejected | Superseded by NNNN | Deprecated
- **Date:** YYYY-MM-DD
- **Decision authority:** Owner or explicitly authorized approver
- **Owners:** Responsibility areas accountable for implementation
- **Requirements:** Applicable stable REQ IDs
- **Issue:** Existing link, or explicitly state no issue exists
- **Implementation evidence:** Pending, or links to actual changes and tests

## Context

Describe the requirement, constraint, problem, and current implementation status. Separate owner-confirmed requirements from new proposals. Link related risks and existing decisions.

## Decision

State the selected behavior, scope, assumptions, compatibility limits, and exclusions. Do not treat acceptance as proof of implementation.

## Alternatives considered

| Alternative | Benefits | Drawbacks | Reason not selected |
| --- | --- | --- | --- |
| Describe each viable alternative | Explain benefits | Explain limitations | Explain selection rationale |

## Consequences

Address customer hosting, credential custody, roles, Assessment, usage correctness, portability, data lifecycle, cost, reliability, support, accessibility, and operational effects as applicable. State when an area is unaffected.

## Validation

Define observable acceptance criteria, negative/failure cases, required evidence, implementation responsibility, and untested assumptions. Reference the [test strategy](../testing.md). Do not invent test results or performance targets.

## Rollback or revisit trigger

Describe rollback/recovery and evidence that would reopen the decision. Supersede earlier ADRs explicitly; never silently rewrite accepted boundaries.
